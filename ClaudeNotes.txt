The weight matrices that would be optimized by Muon (2D matrices excluding embeddings and lm_head) would include:

- [896, 896] for attention projections
- [896, 4864] and [4864, 896] for the MLP layers

These are the matrices that Muon's Newton-Schulz orthogonalization
would be applied to, while parameters like
  embeddings,
  biases, and
  layer norms
would fall back to AdamW optimization.

      # ... many more parameters
  )

  examples/matrix_factorization_compare.py - Simple Factorization Model

  Model: Custom MatrixFactorizationModel
  - Type: Just two parameter matrices, no layers
  - Complexity: Minimal - only 2 matrices
  - Parameters: Just thousands of parameters:
    - factor_A: (matrix_size × rank)
    - factor_B: (matrix_size × rank)
  - Task: Matrix factorization A @ B.T ≈ target_matrix
  - Parameter separation:
    - Muon/MORGN: Both factor matrices (all 2D)
    - AdamW: None (no 1D parameters exist)

  class MatrixFactorizationModel(nn.Module):
      def __init__(self, matrix_size: int, rank: int = None):
          # Only two learnable matrices
          self.factor_A = nn.Parameter(torch.randn(matrix_size, rank) * 0.1)
          self.factor_B = nn.Parameter(torch.randn(matrix_size, rank) * 0.1)

      def forward(self) -> torch.Tensor:
          return self.factor_A @ self.factor_B.T  # Simple matrix multiplication

  Key Differences

  1. Complexity: Language model has ~millions of parameters vs factorization model has ~thousands
  2. Architecture: Transformer vs simple matrix multiplication
  3. Optimization target: All parameters vs only matrix factors benefit from Muon/MORGN
  4. Problem type: Discrete sequence modeling vs continuous matrix approximation

  This explains why the optimizers perform differently on each task - the matrix factorization problem is much more focused on the specific matrix operations that Muon's
  orthogonalization targets, while the language model has many diverse parameter types where only some benefit from orthogonal updates.

      num_hidden_layers=12,

  hidden_size vs intermediate_size

  hidden_size: The main model dimension - size of token embeddings and hidden states throughout the transformer
  - All attention operations work in this dimension
  - Residual connections preserve this size
  - This is what you vary when you change --hidden_size (default 1024)

  intermediate_size: The dimension of the feed-forward network inside each transformer block
  - Each transformer layer has: Attention → Feed-Forward → Next Layer
  - The feed-forward does: hidden_size → intermediate_size → hidden_size
  - It's the "expansion" dimension in the MLP bottleneck
  - Fixed at 4864 in this code (not parameterized)

  Standard Transformer Block Structure:

  Input (hidden_size)
      ↓
  Multi-Head Attention (hidden_size → hidden_size)
      ↓
  Add & Norm
      ↓
  Feed-Forward:
      Linear1: hidden_size → intermediate_size (4864)
      Activation (SiLU)
      Linear2: intermediate_size → hidden_size
      ↓
  Add & Norm
      ↓
  Output (hidden_size)

  So when you set --hidden_size 896, you get a transformer where:
  - Token embeddings are 896-dimensional
  - Attention works in 896D space
  - But the feed-forward layers expand to 4864D internally, then back to 896D

  The intermediate_size is typically 4× the hidden_size, but here it's fixed regardless of your hidden_size setting.

  Feed-forward layers ARE included because:
  - ✅ Linear layer weights are 2D matrices:
    - gate_proj: (4864, 896)

  Gradient Reshaping (lines 216-217):

  if g.ndim > 2:
      g = g.view(g.size(0), -1)

  This handles any higher-dimensional tensors by flattening them into 2D matrices for the Newton-Schulz orthogonalization.

  What Gets Muon vs AdamW:

  ✅ Muon optimizes:
  - All attention weight matrices (Q, K, V, O projections)
  - All feed-forward weight matrices (gate, up, down projections)
  - Any other 2D weight matrices

  ❌ AdamW optimizes:
  - Embedding tables (embed_tokens)
  - Output head weights (lm_head)
  - All bias terms (1D)
  - Layer norm parameters (1D)

> My memory might be fuzzy on Transformer details, but did it originally have both a gate_proj and an up_proj?  I expected only up_proj (plain MLP with one hidden layer).

⏺ You're absolutely right! Your memory is spot-on. 🎯

  Original Transformer (2017) - Simple MLP:

  Feed-Forward Block:
  Linear1: hidden_size → intermediate_size (up projection)
  ReLU activation
  Linear2: intermediate_size → hidden_size (down projection)

  Just two linear layers with ReLU in between - a standard MLP.

  Modern Transformers - Gated MLP:

  The Qwen2 architecture (like many recent models) uses a gated feed-forward network with three linear layers:

  # Modern gated FFN (SwiGLU/GeGLU variant):
  gate = gate_proj(x)      # hidden_size → intermediate_size
  up = up_proj(x)          # hidden_size → intermediate_size
  gated = gate * activation(up)  # Element-wise multiplication
  output = down_proj(gated) # intermediate_size → hidden_size

  Why the Change?

  - Better expressiveness: The gating mechanism lets the network control information flow more selectively
  - SwiGLU/GeGLU: These gated activations often outperform simple ReLU/GELU
  - Used in: LLaMA, PaLM, Qwen, many other modern LLMs

  So you're correct - the original Transformer was much simpler! The gate_proj is a more recent innovation that's become standard in modern language models. The extra matrix
  gives Muon even more 2D weight matrices to apply its orthogonal updates to.

  Classic case of architecture evolution making things more complex but more effective! 📈
